## Phase 7: Product Completion & Target-Host Verification

Phase 6 closed the audit and made the architecture coherent, but the product still has three gaps: (a) the desktop GUI does not yet drive the daemon's topology control plane, (b) some advertised behaviour is silently ignored and some NFRs are unmeasured, and (c) the host-dependent claims in `docs/VV_RTM.md` are still marked *HIL Pending*. Phase 7 closes those.

**Sequencing:** 7.1–7.3 are pure code (any order; 7.1 first is the largest product win); 7.4 extends CI; 7.5/7.6 need target-host runners and are independent of everything else; 7.7 depends on 7.1 (packaged app should be smoke-tested with the live topology UI); 7.8 is parallel housekeeping; 7.9 is optional.

- [x] **Step 7.1 — Wire the desktop GUI to the live topology control plane.** Today `apps/omniport-desktop/src-tauri/src/lib.rs` registers only `fetch_viewport_rows` and `capture_status`; `TopologyCanvas` renders static `initialNodes`/`initialEdges` from `topologyData.ts`, and `onConnect` creates a frontend-only edge. `RpcClient` already exposes `topology()`, `add_route_with_fault()`, `create_virtual_pair()`, `remove_endpoint()`, and `remove_route()`. Deliver: async Tauri commands `get_topology`, `create_virtual_pair`, `remove_endpoint`, `add_route`, `remove_route` (fault-aware) with `Response::Error` codes mapped to actionable UI errors; a frontend topology store fed by `GetTopology` (replacing the static fixtures in Tauri mode); drag-to-connect submits `AddRoute` and reconciles the returned canonical snapshot; node/edge removal actions; loading/error/retry states and post-mutation refresh. Respect IPC ownership: reuse one `RpcClient` for topology calls (do not open a connection per action) and keep the 60 FPS data path untouched. *Acceptance:* daemon-backed integration tests for every new command; a real `omniportd` + WebView2 GUI pass covering create pair / add route / remove route / remove endpoint / unknown-endpoint error; evidence in `gui-test-screenshots/topology_*.png`; no static topology fixture on the shipping path. Closes the ADR-0008 "partial GUI control-plane coverage" consequence. **Done (2026-11-11):** host `topology_store.rs` defines `TopologyControl` with `DaemonTopology` (reconnecting `RpcClient` adapter), `FixtureTopology` (in-process `omniport_core::Topology`, demo-seeded 3 endpoints/2 routes incl. one fault) and `DisconnectedTopology`; `topology_commands.rs` exposes `get_topology`, `create_virtual_pair`, `add_route`, `remove_route`, `remove_endpoint` (all return the canonical snapshot; one cached connection per host, reconnecting once after a daemon restart); `HostTarget` selects capture + topology adapters together. Frontend `topologyClient.ts`/`topologyModel.ts` + live `TopologyCanvas` replace the static fixtures (loading/error/retry, projection with drag-position merge, drag-to-route -> `add_route`, React Flow delete -> `remove_*`, fault attach via remove+add, serialized mutation queue). Evidence: Tauri host 23 tests (17 unit + 3 capture + 3 daemon-backed topology incl. restart reconnect); desktop 102 tests + tsc + vite build; browser GUI 9/9 + 18-point regression; real-daemon WebView2 7/7 (`gui-test-screenshots/p71_tauri_*.png`, `p71_*.png`).
- [x] **Step 7.2 — Harden the daemon control plane.** `crates/omniportd/src/server.rs` currently bounds only the shutdown drain (2 s): any client may hold a connection open indefinitely, and `MAX_FRAME_SIZE` caps frame size but not idle connections, connection count, or request rate. Deliver: per-connection read/write deadline (CLI-configurable with a sane default), a `max_connections` semaphore, idle/request-rate limits, loopback-only bind by default with an explicit `--bind` opt-in for remote control, explicit rejection responses (408/429/503) and log lines on rejection. *Acceptance:* tests for slow/idle clients, a connection storm, oversized frames, and shutdown under load; `.omniport.yaml` scenario remains green; `docs/ICD.md` §3 and `docs/AUDIT_2026-11-10.md` §8 updated. **Done (2026-11-11):** `ServerConfig` + `run_server_with_config` bound concurrency (`--max-connections`, default 64, explicit 503), idle deadline (`--idle-timeout-secs`, default 30, silent close to preserve request/response framing), per-request deadline (`--request-timeout-secs`, default 10, 503) and per-connection rate limit (`--max-requests-per-sec`, default 200, 429); non-loopback `--bind` requires `--allow-remote`; startup validates limits. Evidence: 7 server-unit + 6 CLI-parse + 5 `tests/server_hardening.rs` integration tests (idle close, connection cap 503, 429, oversized frame, shutdown under idle load); `cargo clippy -p omniportd --all-targets -D warnings` clean; `cargo test -p omniportd` green; `.omniport.yaml` scenario still green; ICD §3.4 + AUDIT §8 updated. Remaining: control plane is unauthenticated (remote exposure needs TLS/auth).
- [x] **Step 7.3 — Finish declarative scenario semantics.** `ScenarioRunner` currently ignores `AssertPins.timeout_ms` (checks a locally updated pin map synchronously), and `tcp_server`/`tcp_client`/`udp` endpoint types are accepted and then silently skipped (`runner.rs`: "Network endpoints can be wired when live network testing is configured"). A YAML field that does nothing is a lie in the CI contract. Deliver: honour the pin-assert timeout by waiting for routed `PIN_CHANGE` events up to the deadline (report elapsed time on failure), and either bridge network endpoints through `omniport-net` (mirroring `omniportd`'s `TcpEndpoint`) or reject them at parse time with a clear unsupported-feature error; validate that every YAML field has an effect. *Acceptance:* tests for timeout honoured, late pin change observed, unsupported endpoint type rejected; `.omniport.yaml` end-to-end still green; scenario docs updated. **Done (2026-11-11):** `scenario/validate.rs` rejects unsupported endpoint types (`tcp_server`/`tcp_client`/`udp`), `address`, explicit route ids, undeclared endpoint references, unknown config keys and vacuous steps (`send` with both/neither payload form, empty `set_pins`/`assert_pins`/`assert_metrics`, bare `expect`), plus unknown step keys at parse time; `assert_pins` now honours `timeout_ms` via 10 ms polling of tracked pin state and observes pins applied asynchronously by script endpoints (mirrored from their outbound events); `docs/SCENARIO.md` documents the contract and failure modes. Evidence: 30 CLI tests (8 lib + 12 scenario runner + 10 semantics) including timeout-elapsed and script-applied-pin cases; `.omniport.yaml` green end-to-end; `cargo clippy -p omniport-cli --all-targets -- -D warnings` clean.
